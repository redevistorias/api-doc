Controle de Taxa de Requisições (Rate Limiting)

Para garantir a estabilidade e a qualidade de serviço de nossos ambientes, a API implementa rate limiting por cliente (identificado via oauth_client_id / oauth_user_id e fallback para endereço IP).

Todas as respostas da API contêm os seguintes cabeçalhos de controle:

  • X-RateLimit-Limit: Quantidade máxima de requisições permitidas na janela de tempo.
  • X-RateLimit-Remaining: Número de requisições restantes que podem ser feitas antes do término da janela atual.
  • X-RateLimit-Reset: Timestamp UTC (Unix epoch em segundos) indicando quando o contador de requisições será reiniciado.
  • Retry-After: Tempo de espera (em segundos) retornado caso o limite de requisições seja ultrapassado.

Caso você atinja o limite máximo estabelecido, a API retornará o status HTTP 429 Too Many Requests. Recomendamos adotar backoff exponencial e respeitar o tempo informado no cabeçalho Retry-After.

Autenticação

Para a integração de um serviço externo com a API da Rede Vistorias é necessária a utilização de uma API Key fornecida pelo usuário (ou adquirida no cadastro do cliente). Possuindo uma API Key é possível gerar um 'Bearer token' com validade de 24 horas, a contar do momento de sua geração. Este token é obrigatório em todos os requests na API da Rede Vistorias.

Gera o token de acesso

Esta requisição aceita dois tipos de "grant_type":

  • api_key: O token gerado neste tipo de requisição é utilizado para fazer novos pedidos na API (utilizado nas requisições de Pedidos ou Price Preview)
  • client_credentials: Utilizado para cadastrar novos clientes e integrações em nossa API.

Pedidos

A API da Rede Vistorias provê uma forma de serviços externos para realizar pedidos de vistorias. Todas alterações no pedido que sejam relevantes para o cliente serão notificadas por um webhook no endpoint informado no momento da geração da API Key. Cada webhook possui um formato específico para a ação que ele representa.

Cadastra um novo pedido de vistoria na API da Rede Vistorias.

O retorno é o código cadastrado da vistoria, e o preço que será consumido do pacote contratado pelo cliente, em créditos.
No caso do pedido de saída ou de conferência, deve ser informada a inspeção anterior. Isto pode ser feito de duas formas, fazendo o upload de um arquivo (ver Upload URL) ou informando um link já existente, que será processado por nossa plataforma. Para pedidos de aditivo, deve-se obrigatoriamente informar apenas o código do pedido anterior, sendo ele um pedido de entrada ou um outro pedido de aditivo.

Override de webhook: É possível informar opcionalmente os campos webhook_url e webhook_secret para que todas as notificações deste pedido específico sejam enviadas para uma URL customizada, assinadas com o secret informado. Quando presentes, os hooks padrão da integração são ignorados para este pedido. Atenção: Caso este pedido utilize a mesma URL e secret padrão já configurados na integração ou no cadastro da imobiliária, omita estes campos do payload.

Cancelar ou excluir um pedido.

Cancela ou exclui um pedido de vistoria solicitado.

  • Pedidos no status WAITING (recém-solicitados): O pedido é cancelado/excluído do sistema e os créditos consumidos são estornados. O webhook de cancelamento não é disparado nesse caso.
  • Pedidos no status ACCEPTED (aceitos pela franquia, antes da atribuição de vistoriador): O pedido tem seu status alterado para CANCELED e os créditos consumidos são estornados integralmente sem cobrança de taxa de cancelamento. O webhook de cancelamento (order.canceled) é disparado.
    Obs.: Caso o pedido já possua vistoriador atribuído, já esteja em andamento, já tenha sido finalizado ou já esteja cancelado, o cancelamento não será permitido e retornará erro 400 com o código do motivo correspondente.

Webhook

O serviço da Rede Vistorias utiliza webhooks para notificar a ferramenta de integração ou o sistema da imobiliária sobre qualquer alteração no ciclo de vida do pedido de vistoria.

1. Configuração de URL (Padrão vs. Por Imobiliária)

A URL de destino dos webhooks pode ser configurada de duas maneiras:

  • URL Padrão da Integração: Uma URL única e centralizada para todos os clientes que utilizam o ERP/integração.
  • URL Variável por Cliente/Imobiliária: Cada imobiliária parceira pode definir sua própria URL de webhook diretamente no momento da ativação da integração em seu painel da Rede Vistorias (momento em que a sua API Key é gerada).

2. Override de Webhook por Pedido

Ao criar um pedido (POST /orders), é possível informar opcionalmente os campos webhook_url e webhook_secret para direcionar as notificações exclusivamente daquele pedido para uma URL ou chave específica:

  • Atenção (Regra de Omissão): Caso o pedido utilize a mesma URL e secret padrão já configurados na integração ou no cadastro da imobiliária, você deve omitir as chaves webhook_url e webhook_secret do payload. Envie-as apenas quando for estritamente necessário substituir o destino padrão para aquele pedido específico.

3. Tabela de Eventos e Gatilhos

Todos os webhooks enviam payloads no formato JSON via método POST. Abaixo estão os eventos emitidos e seus significados:

Evento Status do Pedido Descrição / Momento do Disparo
order.created ACCEPTED Emitido assim que o pedido é aprovado e aceito pela franquia responsável.
order.assigned ACCEPTED Emitido quando um vistoriador é atribuído e a data/horário é agendada para execução.
order.finished FINISHED Emitido quando a vistoria é concluída, com laudos e links finais disponíveis.
order.rejected REJECTED Emitido quando o pedido não pode ser atendido pela franquia e é recusado.
order.canceled CANCELED Emitido quando um pedido já aceito é cancelado (via integração ou franquia). (Nota: exclusão de pedidos em WAITING não dispara webhook).
order.divergence.created FINISHED Emitido quando uma contestação/divergência de laudo é apontada.
order.divergence.waiting_client FINISHED Emitido quando a análise da contestação é realizada e aguarda aprovação da imobiliária.
order.divergence.finished FINISHED Emitido quando a análise da contestação é concluída e o relatório final fica disponível.

4. Autenticação e Segurança (HMAC-SHA256)

Todas as requisições de webhook enviadas pela Rede Vistorias incluem o cabeçalho HTTP:

X-Webhook-Signature: sha256=<hash>
  • Chave Secreta (Secret): Por padrão, a assinatura é gerada utilizando a api_key da integração/imobiliária como secret (ou o webhook_secret, caso tenha sido informado override no pedido).
  • Algoritmo: HMAC com algoritmo SHA-256.

Como Validar a Assinatura (Exemplo em Python):

Importante: Sempre utilize o corpo bruto da requisição (raw request body) como bytes para o cálculo do hash, antes de qualquer parsing ou deserialização JSON.

import hmac
import hashlib

# 1. Recupera a assinatura do cabeçalho
signature_header = request.headers.get('X-Webhook-Signature', '')
signature = signature_header.replace('sha256=', '')

# 2. Secret: api_key da integração (ou webhook_secret do override)
secret = api_key.encode('utf-8')

# 3. Calcula o HMAC com os bytes brutos do corpo da requisição (raw body)
expected_signature = hmac.new(
    secret,
    request.body,  # raw bytes
    hashlib.sha256
).hexdigest()

# 4. Comparação em tempo constante para evitar timing attacks
is_valid = hmac.compare_digest(expected_signature, signature)
if not is_valid:
    raise PermissionError("Assinatura de webhook inválida!")

5. Boas Práticas para o Integrador

  • Resposta Rápida (HTTP 200 OK): Seu endpoint deve responder com status 200 OK assim que receber o webhook, antes de processar tarefas pesadas de banco de dados ou download de fotos. Processe o payload de forma assíncrona (em background / filas) para evitar timeout.
  • Idempotência: Como webhooks podem sofrer retentativas automáticas em caso de instabilidade na rede, certifique-se de que seu endpoint processe o mesmo evento (code + event) de forma idempotente sem duplicar registros.

Simulação de Webhook (Sandbox)

Endpoints dedicados para testes em ambiente Sandbox (ou de desenvolvimento). Permite que integradores solicitem o disparo manual de eventos de webhook para seus pedidos, facilitando testes de fluxo e recepção de notificações sem a necessidade de intervenção operacional manual.

Atenção: Esta rota é terminantemente desabilitada em ambiente de produção (retornará HTTP 403 Forbidden).

Regras de Transição de Estado:

Evento Pré-requisito do Pedido Descrição / Efeito
ACCEPTED Status deve estar em WAITING Aprova o pedido, marcando status como ACCEPTED e disparando evento order.accepted.
REJECTED Status deve estar em WAITING Rejeita o pedido, marcando status como REJECTED e disparando evento order.rejected.
ASSIGNED Status deve estar em ACCEPTED Atribui vistoriador, agenda a vistoria e enfileira evento inspection.assign (dispara webhook inspection.assigned).
CANCELED Status em WAITING ou ACCEPTED Cancela o pedido, desvincula vistorias e dispara webhook order.canceled.
FINISHED Status em ACCEPTED Finaliza a vistoria com dados e fotos no S3 (conforme modalidade entrada, saida ou conferencia), define status como FINISHED e dispara webhook order.finished. Auto-atribui vistoriador caso ainda não atribuído.
DIVERGENCE_CREATED Status deve estar em FINISHED Cria apontamento de contestação do laudo e dispara webhook order.divergence.created.
DIVERGENCE_WAITING_CLIENT Status deve estar em FINISHED Atualiza contestação com parecer da franqueadora e dispara webhook order.divergence.waiting_client.
DIVERGENCE_FINISHED Status deve estar em FINISHED Conclui contestação com parecer do cliente e dispara webhook order.divergence.finished.

Solicitar simulação de disparo de webhook (Apenas Sandbox).

Dispara a transição de estado de um pedido e a emissão do webhook correspondente no ambiente Sandbox ou Dev. A resposta é processada de forma assíncrona, retornando HTTP 202 Accepted acompanhado dos eventos disparados no broker.

Restrições:

  • Esta funcionalidade não funciona em produção (retorna 403 Forbidden).
  • O pedido deve pertencer à mesma imobiliária/cliente associado à credencial de acesso (caso contrário retorna 403 Forbidden).
  • O pedido deve estar no status pré-requisito do evento solicitado (caso contrário retorna 422 Unprocessable Entity).
